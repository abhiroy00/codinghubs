What should a beginner API test verify?

API testing checks whether a request produces the expected status, headers, data and side effects. A successful response alone does not prove correctness. Pair a valid request with missing-input, wrong-type, unauthorized and missing-resource cases. Confirm that a rejected write did not change stored data.

Use a local practice service or an explicitly designated demo API. Keep tokens out of collection exports, use environment variables and state the expected result for each test before running it. The Postman quick start explains request and response inspection. Continue with test-case design or compare the Automation Testing learning topics.

Most applications are built on APIs: the mobile app, the website and partner systems all talk to the same back-end services. Testing those APIs directly is faster and more reliable than testing everything through the user interface. This API testing tutorial covers the basics, manual testing with Postman and automated API tests in code.

API basics you need

A REST API receives an HTTP request and returns a response, usually JSON.

MethodPurposeTypical success code
GETRead data200 OK
POSTCreate something201 Created
PUT / PATCHReplace or update200 OK
DELETERemove204 No Content

Errors matter just as much: 400 (bad input), 401 (not logged in), 403 (not allowed), 404 (not found), 409 (conflict) and 500 (server error).

What to check in an API test

  • Status code is correct for the scenario.
  • Response body has the right fields, types and values.
  • Schema matches the contract (no missing or renamed fields).
  • Headers, such as content type.
  • Negative cases: missing fields, invalid values, wrong types.
  • Security: unauthenticated or unauthorised requests are rejected, and users cannot read other users' data.
  • Response time is acceptable.

Step 1: Explore with Postman

  1. Create a request: choose the method, enter the URL, add headers and a JSON body.
  2. Send it and inspect the status, body and time.
  3. Save requests in a collection and use environment variables for base URLs and tokens.
  4. Add tests in the Tests tab, for example checking the status code.
pm.test("status is 200", () => pm.response.to.have.status(200));
pm.test("returns a list", () => pm.expect(pm.response.json()).to.be.an("array"));

Collections can be run automatically from the command line with Newman, which is handy for CI.

Step 2: Automate with Python (requests + pytest)

import requests

BASE = "https://jsonplaceholder.typicode.com"


def test_get_post():
    r = requests.get(f"{BASE}/posts/1", timeout=10)
    assert r.status_code == 200
    body = r.json()
    assert body["id"] == 1
    assert isinstance(body["title"], str)


def test_create_post():
    payload = {"title": "Hello", "body": "API testing", "userId": 1}
    r = requests.post(f"{BASE}/posts", json=payload, timeout=10)
    assert r.status_code == 201
    assert r.json()["title"] == "Hello"

JSONPlaceholder is a free public fake API for practice; it does not really save data.

Step 3: Automate with Java (REST Assured)

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

@Test
public void getPostReturnsTitle() {
    given()
        .baseUri("https://jsonplaceholder.typicode.com")
    .when()
        .get("/posts/1")
    .then()
        .statusCode(200)
        .body("id", equalTo(1));
}

Step 4: Handle authentication

Most real APIs need a token. A common pattern: call the login endpoint once in a fixture or setup method, store the token, and send it as Authorization: Bearer <token> in later requests. Keep credentials in environment variables, never in the code repository.

Step 5: Organise and run in CI

  • Put the base URL and credentials in configuration per environment (local, staging).
  • Create test data through the API and clean it up afterwards, so tests are independent.
  • Run the suite in CI on every change; see building a test automation framework.

Common mistakes

  • Checking only the status code and not the body.
  • Testing only the happy path.
  • Tests that depend on data created by another test.
  • Hard-coded tokens that expire.
  • Running destructive tests against production.

API testing vs UI testing

API tests are faster, less flaky and pinpoint back-end problems. UI tests confirm the whole user journey. A healthy suite has more API tests than UI tests, following the test pyramid described in what is automation testing.

===FAQ=== Q: What is API testing? A: API testing checks that an application's APIs return the correct status codes, data, errors and security behaviour, by sending requests directly instead of using the user interface. Q: Is Postman enough for API testing? A: Postman is excellent for exploring and building collections, and Newman can run them automatically. Many teams also write API tests in code for better version control and reuse. Q: Which language is best for API test automation? A: Python with requests and pytest, and Java with REST Assured, are both popular. JavaScript is also common with Playwright's API testing features. Q: Do I need coding knowledge for API testing? A: Manual API testing with Postman needs little coding. Automated API testing needs basic programming in Python, Java or JavaScript.
