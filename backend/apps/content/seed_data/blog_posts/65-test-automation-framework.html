Scripts become a test automation framework when they are organised, configurable, reliable and easy for the whole team to run. This guide builds a practical framework with Python, pytest, Playwright and the Page Object Model, then runs it automatically on every code change. The same structure works in Java with Selenium and TestNG.

What a good framework provides

  • A clear folder structure so anyone can find tests and pages.
  • Configuration per environment (local, staging) without code changes.
  • Reusable setup and teardown (fixtures).
  • Maintainable locators through page objects.
  • Independent test data.
  • Readable reports with screenshots or traces on failure.
  • Fast, parallel runs in CI.

Step 1: Folder structure

qa-framework/
  pages/            base_page.py, login_page.py, cart_page.py
  tests/
    ui/             test_login.py, test_checkout.py
    api/            test_orders_api.py
  data/             users.json
  conftest.py       fixtures: config, browser page, API client
  pytest.ini        markers and default options
  requirements.txt
  .github/workflows/tests.yml

Step 2: Install and configure

pip install pytest pytest-playwright pytest-xdist pytest-html requests
playwright install --with-deps chromium
# pytest.ini
[pytest]
addopts = -v --html=report.html --self-contained-html
markers =
    smoke: quick checks for every commit
    regression: full suite

Step 3: Configuration through environment variables

# conftest.py
import os
import pytest
import requests


@pytest.fixture(scope="session")
def base_url():
    return os.environ.get("BASE_URL", "http://localhost:3000")


@pytest.fixture(scope="session")
def api(base_url):
    session = requests.Session()
    session.headers["Authorization"] = f"Bearer {os.environ.get('API_TOKEN', '')}"
    session.base_url = base_url
    return session

Secrets such as tokens and passwords come from environment variables or the CI secret store, never from the repository.

Step 4: Page objects

# pages/login_page.py
from playwright.sync_api import Page


class LoginPage:
    def __init__(self, page: Page, base_url: str):
        self.page = page
        self.base_url = base_url

    def open(self):
        self.page.goto(f"{self.base_url}/login")
        return self

    def login(self, email: str, password: str):
        self.page.get_by_label("Email").fill(email)
        self.page.get_by_label("Password").fill(password)
        self.page.get_by_role("button", name="Log in").click()

Read the full pattern in the Page Object Model guide.

Step 5: Tests with markers

# tests/ui/test_login.py
import pytest
from playwright.sync_api import Page, expect
from pages.login_page import LoginPage


@pytest.mark.smoke
def test_valid_login(page: Page, base_url):
    LoginPage(page, base_url).open().login("student@example.com", "secret123")
    expect(page.get_by_role("heading", name="Dashboard")).to_be_visible()

Run only quick checks with pytest -m smoke, or everything with pytest.

Step 6: Independent test data

  • Create the data each test needs (ideally through the API) and clean it up afterwards.
  • Use unique values, such as an email with a timestamp, so parallel tests do not collide.
  • Never depend on another test having run first.

Step 7: Reports, traces and parallel runs

  • pytest-html produces a shareable HTML report.
  • Playwright can record traces and screenshots on failure (--tracing retain-on-failure --screenshot only-on-failure).
  • pytest-xdist runs tests in parallel: pytest -n auto.

Step 8: Run in CI with GitHub Actions

# .github/workflows/tests.yml
name: tests
on: [push, pull_request]
jobs:
  ui-and-api:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: playwright install --with-deps chromium
      - run: pytest -n auto --tracing retain-on-failure
        env:
          BASE_URL: ${{ secrets.STAGING_URL }}
          API_TOKEN: ${{ secrets.API_TOKEN }}
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: test-report
          path: |
            report.html
            test-results/

Every push now runs the suite, and the report and failure traces are downloadable from the workflow run. Jenkins and GitLab CI follow the same steps.

Keeping the framework healthy

  • Fix or quarantine flaky tests quickly; do not hide them with endless retries.
  • Review test code like production code.
  • Keep the smoke suite fast so developers get feedback in minutes.
  • Delete tests that no longer add value.

===FAQ=== Q: What is a test automation framework? A: A test automation framework is an organised set of code, conventions and tools, such as page objects, configuration, test data, reporting and CI, that makes automated tests reliable and easy to maintain. Q: Which framework type is best: data-driven, keyword-driven or hybrid? A: Most teams use a hybrid approach: Page Object Model for structure, data-driven tests where useful, and shared utilities, configuration and reporting. Q: Can I build a framework with Selenium and Java instead? A: Yes. The same structure applies with Selenium, TestNG or JUnit, Maven or Gradle, and a CI tool such as Jenkins or GitHub Actions. Q: How do I run automated tests in CI? A: Configure a pipeline to install dependencies and browsers, run tests headlessly on each push or pull request, and publish reports and failure screenshots as artifacts.
