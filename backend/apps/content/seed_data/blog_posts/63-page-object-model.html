When you write your first few automated tests, it is natural to put locators and clicks directly inside each test. After fifty tests, a single change to the login page can break dozens of them. The Page Object Model (POM) solves this by giving every page or component its own class that knows how to interact with it, so tests describe what the user does and page classes handle how.

The problem POM solves

# Without POM: locators repeated in every test
driver.find_element(By.ID, "email").send_keys("a@example.com")
driver.find_element(By.ID, "password").send_keys("secret123")
driver.find_element(By.CSS_SELECTOR, "button[type='submit']").click()

If the button's selector changes, you have to update it everywhere. With POM, you update it in one place.

A page class example (Python + Selenium)

# pages/login_page.py
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait


class LoginPage:
    EMAIL = (By.ID, "email")
    PASSWORD = (By.ID, "password")
    SUBMIT = (By.CSS_SELECTOR, "button[type='submit']")
    ERROR = (By.CSS_SELECTOR, "[role='alert']")

    def __init__(self, driver, base_url):
        self.driver = driver
        self.base_url = base_url
        self.wait = WebDriverWait(driver, 10)

    def open(self):
        self.driver.get(f"{self.base_url}/login")
        return self

    def login(self, email, password):
        self.wait.until(EC.visibility_of_element_located(self.EMAIL)).send_keys(email)
        self.driver.find_element(*self.PASSWORD).send_keys(password)
        self.driver.find_element(*self.SUBMIT).click()
        return DashboardPage(self.driver)

    def error_message(self):
        return self.wait.until(EC.visibility_of_element_located(self.ERROR)).text


class DashboardPage:
    HEADING = (By.TAG_NAME, "h1")

    def __init__(self, driver):
        self.driver = driver

    def heading(self):
        return WebDriverWait(self.driver, 10).until(EC.visibility_of_element_located(self.HEADING)).text

Tests become short and readable

# tests/test_login.py
from pages.login_page import LoginPage


def test_valid_login(driver, base_url):
    dashboard = LoginPage(driver, base_url).open().login("student@example.com", "secret123")
    assert dashboard.heading() == "Dashboard"


def test_wrong_password_shows_error(driver, base_url):
    page = LoginPage(driver, base_url).open()
    page.login("student@example.com", "wrong")
    assert "Invalid" in page.error_message()

Best practices

  • Keep assertions in tests, not in page classes. Page methods return data or other pages; tests decide what is correct.
  • Name methods after user actions: login(), add_to_cart(), not click_button_3().
  • Return the next page object from navigation methods, as login() returns DashboardPage.
  • Put waits inside page methods so tests do not repeat synchronisation logic.
  • Use components for parts shared across pages, such as headers or modals.
  • Prefer stable locators such as IDs or data-testid attributes.

Common mistakes

  • Huge "god" page classes containing everything.
  • Exposing raw locators to tests instead of meaningful methods.
  • Assertions hidden inside page methods, which makes failures confusing.
  • Copying the same helper code into every page instead of a base page class.

A typical folder structure

automation/
  pages/        login_page.py, dashboard_page.py, base_page.py
  tests/        test_login.py, test_cart.py
  utils/        config.py, data.py
  conftest.py   driver and base_url fixtures
  pytest.ini

The same pattern works in Java with TestNG, and in Playwright, where page classes wrap page.get_by_role() locators.

===FAQ=== Q: What is the Page Object Model? A: The Page Object Model is a test automation design pattern where each page or component has a class containing its locators and actions, keeping tests readable and easy to maintain. Q: Should assertions be inside page objects? A: Generally no. Page objects should perform actions and return information; tests should contain the assertions that decide pass or fail. Q: Is POM only for Selenium? A: No. The pattern works with Playwright, Cypress, Appium and other UI automation tools. Q: What is Page Factory? A: Page Factory is a Java Selenium helper that initialises page elements using annotations. It is optional; many teams use plain page classes with By locators instead.
