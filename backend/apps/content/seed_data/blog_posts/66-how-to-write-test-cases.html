Good testing starts long before any script runs. A well-written test case tells anyone exactly what to check, how to check it and what result proves the feature works. This guide shows how to write test cases with a standard format, a complete example and the techniques testers use to choose what to test.

What is a test case?

A test case is a set of conditions, steps and expected results used to verify one specific behaviour of an application. Test cases are grouped into test suites, linked to requirements or user stories, and executed manually or by automation.

Standard test case format

FieldWhat to write
Test case IDA unique reference, e.g. TC_LOGIN_001
TitleShort and specific: "Login succeeds with valid email and password"
Requirement / storyThe feature or story it verifies
PreconditionsWhat must be true first: a registered user exists
Test dataExact inputs to use
StepsNumbered, one action per step
Expected resultThe observable outcome that means pass
Actual result and statusFilled in during execution: pass, fail or blocked
PriorityHigh, medium or low

Worked example: login

TC_LOGIN_001: Login succeeds with valid credentials

  • Preconditions: user student@example.com exists with password Secret@123.
  • Steps:
    1. Open the login page.
    2. Enter student@example.com in Email.
    3. Enter Secret@123 in Password.
    4. Click Log in.
  • Expected result: the dashboard opens and shows "Welcome, Student".
  • Priority: High.

Related negative cases for the same feature:

  • TC_LOGIN_002: wrong password shows "Invalid email or password" and does not log in.
  • TC_LOGIN_003: empty email shows a required-field message.
  • TC_LOGIN_004: invalid email format is rejected.
  • TC_LOGIN_005: account is temporarily locked after the configured number of failed attempts (if the requirement says so).

Techniques for choosing test cases

Equivalence partitioning

Divide inputs into groups that should behave the same, and test one value from each. For an age field accepting 18–60: one valid value (30), one below (10) and one above (70).

Boundary value analysis

Bugs cluster at edges. For 18–60, test 17, 18, 19, 59, 60 and 61.

Decision tables

When results depend on combinations of conditions (for example, discount rules by membership and order value), list each combination and its expected outcome.

State transitions

For features with states, such as an order moving from placed to shipped to delivered, test valid and invalid transitions.

Best practices

  • One behaviour per test case. Small cases are easier to run, automate and debug.
  • Write expected results precisely. "Works correctly" is not testable; "shows order number and status Placed" is.
  • Include negative and edge cases, not only the happy path.
  • Use clear, simple language so a new team member can execute it.
  • Keep test data explicit and reusable.
  • Link to requirements so coverage gaps are visible.
  • Review test cases with developers and business analysts.

Writing a good bug report

When a test fails, report it with a clear title, environment, exact steps, expected versus actual result, screenshots or logs, and severity. A reproducible bug report saves hours of back-and-forth.

From test cases to automation

Stable, high-priority and frequently repeated test cases are the best candidates for automation. Each step maps to a page-object method and each expected result to an assertion. Read manual vs automation testing, then start automating with the Selenium tutorial and the Page Object Model.

===FAQ=== Q: What should a test case contain? A: A unique ID, a clear title, preconditions, test data, numbered steps, an expected result, priority, and fields for the actual result and status during execution. Q: What is the difference between a test case and a test scenario? A: A test scenario is a high-level description of what to test, such as "user login". Test cases are the detailed steps and expected results that cover that scenario. Q: How many test cases should one feature have? A: Enough to cover the main positive path, important negative cases and boundaries. Techniques such as equivalence partitioning and boundary value analysis keep the number manageable. Q: Which tools are used to manage test cases? A: Teams use spreadsheets for small projects and test management tools such as Jira with test plugins, TestRail or Azure Test Plans for larger ones.
