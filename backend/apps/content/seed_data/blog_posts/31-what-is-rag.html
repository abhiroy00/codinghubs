What does RAG mean in practice?

Retrieval-augmented generation (RAG) retrieves relevant information and supplies it as context to a language model before an answer is generated. The model weights do not need to change each time a source document changes. Retrieval can still miss evidence, and a model can still make unsupported claims: citations, permission checks and evaluation remain necessary.

Large language models are impressive, but they have two big limits: they do not know your private data, and their built-in knowledge stops at their training date. Retrieval-augmented generation, or RAG, solves both. If you have wondered what is RAG and why every AI job description mentions it, this guide explains the idea and the full pipeline in simple terms.

The problem RAG solves

Imagine asking a chatbot, "What is the refund policy for the Java course?" A general LLM has never seen your institute's policy, so it might guess, and a confident guess is worse than no answer. You could paste the whole policy document into every prompt, but real organisations have thousands of documents, far too many to include every time.

RAG works like an open-book exam: before answering, the system retrieves the most relevant passages from your documents and gives them to the model, which then generates an answer grounded in that material.

RAG in one picture

  1. Question: "What is the refund policy for the Java course?"
  2. Retrieve: search your documents and find the three most relevant passages.
  3. Augment: add those passages to the prompt with instructions.
  4. Generate: the LLM answers using only the provided passages, ideally citing them.

Key concept: embeddings

An embedding is a list of numbers that represents the meaning of a piece of text. Texts with similar meanings have embeddings that are close together, even if they use different words. "How do I get my money back?" and "refund policy" end up near each other, which keyword search would miss.

Embedding models are available through AI APIs and as open-source models. You convert both your documents and the user's question into embeddings, then find the document chunks closest to the question.

The RAG pipeline step by step

Phase 1: Indexing (done in advance)

  1. Load documents: PDFs, web pages, policies, help articles, database records.
  2. Clean the text: remove navigation menus, headers, footers and duplicate content.
  3. Chunk: split documents into passages, often a few hundred words each, with a small overlap so ideas are not cut in half. Splitting at headings and paragraphs usually works better than fixed character counts.
  4. Embed: create an embedding for each chunk.
  5. Store: save chunks, embeddings and metadata (source, title, date, access rights) in a vector database or a database with vector search.

Phase 2: Answering (for every question)

  1. Embed the question.
  2. Search: find the most similar chunks, optionally filtered by metadata such as course or date.
  3. Rerank (optional): use a reranking model to reorder results by relevance.
  4. Build the prompt: instructions plus retrieved chunks plus the question.
  5. Generate: the LLM writes the answer and cites the sources.

A simplified example in Python

def answer(question, store, embed, llm):
    query_vector = embed(question)
    chunks = store.search(query_vector, top_k=4)

    context = "\n\n".join(f"[{i + 1}] {c.text}" for i, c in enumerate(chunks))
    prompt = (
        "Answer the question using only the sources below. "
        "Cite sources like [1]. If the answer is not in the sources, "
        "say you do not know.\n\n"
        f"Sources:\n{context}\n\nQuestion: {question}"
    )
    return llm(prompt), chunks

Here embed, store and llm stand for your embedding model, vector store and LLM client.

Vector databases

A vector database stores embeddings and finds the nearest ones quickly. Options include dedicated vector databases, PostgreSQL with the pgvector extension, and vector search features in many existing databases and search engines. For learning and small projects, pgvector or a lightweight local library is often enough.

Hybrid search

Embedding search understands meaning but can miss exact terms such as course codes, error messages or names. Many production systems combine vector search with traditional keyword search (hybrid search) to get the best of both.

Evaluating a RAG system

A RAG demo is easy; a reliable RAG system needs measurement. Create a test set of real questions with expected answers and check:

  • Retrieval quality: did the search return the passages containing the answer?
  • Faithfulness: does the answer stick to the retrieved sources without inventing details?
  • Answer quality: is it correct, complete and clear?
  • Refusals: does it say "I do not know" when the answer is not in the documents?

Run the test set every time you change chunking, embeddings, prompts or models.

Common mistakes

  • Chunks that are too large (irrelevant text dilutes the answer) or too small (context is lost).
  • Indexing messy text full of menus and boilerplate.
  • No metadata, so you cannot filter by date, product or permissions.
  • Ignoring access control, so users can retrieve documents they should not see.
  • Never re-indexing when documents change.
  • No evaluation, so quality problems go unnoticed.

RAG vs fine-tuning

Fine-tuning changes a model's behaviour or style by training it further on examples. RAG gives a model access to knowledge at question time. For "answer from our documents", RAG is usually the better first choice: it is cheaper, easier to update and can cite sources. Fine-tuning is better for teaching a consistent format, tone or specialised task.

===FAQ=== Q: What is RAG in AI? A: RAG, or retrieval-augmented generation, is a technique where an AI system first retrieves relevant information from a knowledge source and then uses it to generate a grounded answer. Q: Why is RAG important? A: RAG lets language models answer from private or recent information without retraining, reduces hallucinations, and allows answers to cite their sources. Q: Do I need a vector database for RAG? A: You need some way to search embeddings. That can be a dedicated vector database, PostgreSQL with pgvector, a search engine with vector support or, for small projects, an in-memory library. Q: Is RAG better than fine-tuning? A: For answering questions from changing documents, RAG is usually better and cheaper. Fine-tuning is more suitable for teaching a model a specific style, format or task.
