# concept
## Start with a task rather than a product label
Artificial intelligence is a field concerned with constructing computational systems that perform tasks associated with intelligent behavior. Those tasks include searching for a solution, reasoning from available information, interpreting observations, learning useful patterns and selecting actions. There is no single product architecture that defines every AI system. A program can use explicit rules and search without learning from data; another can learn a statistical model; a larger application can combine both. Calling all of them AI does not make their capabilities or failure modes identical.

To study the field as an engineer, replace an impressive label with a concrete task. What information enters the system? What result must it produce? Which actions may it take? What counts as success? Who is affected by a mistake? These questions turn a vague ambition into something you can implement and test. Our running example is a support workflow that proposes a sequence of permitted steps toward resolving a ticket. It is deliberately small enough that you can inspect every assumption and independently verify its answers.

## Observations, representations, actions and goals
An observation is information available to the system, such as a ticket's category or the current stage of a workflow. A representation is the form in which the program stores and reasons about that information. A list of workflow stages and allowed transitions is one representation; a numerical vector extracted from ticket text is another. Representations make computation possible, but they also leave information out. A workflow graph cannot express every nuance of a conversation unless those details are explicitly represented somewhere else.

An action changes something or requests a change. Sending a draft for review, asking for missing information and calling a restricted service can all be actions. A goal specifies a desired condition, such as identifying a permitted route to a resolved state. The goal must be distinguished from an evaluation measure. Reaching a state named resolved in a simulation is not evidence that a customer's problem was actually solved. The application needs a way to connect its internal representation with outcomes in the real environment.

## The agent viewpoint
An agent is a system that receives observations and chooses actions within an environment. This viewpoint is useful because it makes the relationship between information and behavior explicit. A reactive agent might choose an action from the latest observation. A planning agent can consider a sequence of future states before acting. A learning component may improve a prediction from experience. None of these descriptions implies consciousness, unrestricted autonomy or an understanding of everything a person might mean.

For our ticket example, the environment includes the ticket database, support policies and people who approve sensitive actions. The planner receives a graph and a start and goal state. Its output is a proposed route, not permission to execute that route. Keeping proposal and execution separate is an architectural decision: the application can reject an otherwise valid route if it conflicts with current authorization, stale policy or a human decision. As you encounter more complex agents later, retain this distinction between proposing an action and having the authority to perform it.

## Why multiple AI approaches exist
Different tasks provide different kinds of structure. A well-specified puzzle can often be solved by searching legal states. An expert-maintained policy can sometimes be represented by rules. Recognizing an image may require a model that learns useful patterns from many examples. Producing a draft response may benefit from a generative model. Each choice depends on the task, the available information and the evidence needed to trust the result.

Historically, AI research has included symbolic reasoning, search, knowledge representation, statistical learning and neural approaches. These are overlapping research traditions rather than a clean sequence in which each new method made every older one obsolete. Modern systems still use ordinary data validation, explicit constraints, retrieval and search alongside learned models. The useful lesson from this evolution is methodological: choose mechanisms because they address a task's requirements, and measure the resulting system. Do not assume that using a newer or larger model automatically improves the decision you care about.

## Represent the support problem as a graph
A graph consists of nodes and edges. Here a node is a workflow stage, and a directed edge means that the application considers a transition between two stages possible. The edge received → verified permits movement from received to verified; it does not automatically permit the reverse movement. A route is a sequence of nodes connected by edges. A shortest route in an unweighted graph uses the fewest edges among all valid routes from the start to the goal.

The representation makes the computational problem precise, but its meaning remains an application responsibility. If the graph includes an invalid transition, a correct graph-search algorithm can confidently return an operationally invalid route. If an important stage is missing, the algorithm cannot invent it. Before optimizing the search, inspect the state model with domain specialists. Ask which transitions are always legal, which depend on current evidence and which require a separate permission check immediately before execution.

## Breadth-first search step by step
Breadth-first search explores a graph in layers. It starts with the start node, then considers nodes reachable in one edge, then two edges, and so on. A queue holds nodes waiting to be explored. The oldest queued node is processed first. When the algorithm discovers a previously unseen neighbor, it records the node that led to that neighbor and adds the neighbor to the queue. Recording discovery prevents a cycle from causing the same node to be added indefinitely.

When the goal is removed from the queue, the recorded parent links reconstruct a route back to the start. Reversing that chain produces the requested forward route. Because nodes are explored in nondecreasing edge distance, the first discovered route to a node has minimum edge count in an unweighted graph. That guarantee depends on the representation and algorithm assumptions. It says nothing about monetary cost, elapsed time or customer satisfaction if those quantities are not encoded as edge weights and handled by an appropriate algorithm.

## A small mathematical model
Let V be the set of nodes and E the set of directed edges. A route r = (v₀, v₁, …, v_k) is valid when every consecutive pair (vᵢ, vᵢ₊₁) belongs to E. Its unweighted length is k, the number of transitions, rather than the number of listed nodes. The search objective is to find a valid route with minimum k such that v₀ is the start and v_k is the goal. If no such route exists, the correct result is an explicit no-route outcome.

For adjacency-list graph storage, ordinary breadth-first traversal visits at most each reachable node and its outgoing edges once, giving O(|V| + |E|) traversal work. The vertical bars mean the number of elements in a set, and O describes how work grows with input size. The implementation also sorts neighbors to make ties deterministic, so that sorting adds work beyond this basic traversal bound. Its parent table and queue require space proportional to the number of discovered nodes. These costs matter when an apparently simple workflow expands into a large state space.

## Searching is different from learning
Our graph planner does not learn the graph from ticket history. A person supplies the transitions, and the program searches them when asked. Running the same query twice does not train it or improve its policy. This is still a useful example of a classic AI problem-solving technique. It demonstrates why AI and machine learning should not be treated as interchangeable terms.

A learned ticket classifier would solve a different problem: mapping observations to likely categories using patterns fitted from examples. A planning application could use that category to select a workflow, but classification errors would then become an upstream source of planning errors. A generative model could explain a proposed route in natural language, but a fluent explanation would not prove the route was permitted. Analyze each component separately, then test the interactions. A composite system inherits failure modes from the connections as well as the individual algorithms.

## Correctness has several layers
Algorithmic correctness asks whether a procedure implements its stated mathematical contract. Input correctness asks whether the provided data matches that contract. Domain correctness asks whether the representation reflects the real task. Operational correctness asks whether the system behaves appropriately under actual permissions, timeouts, changing information and user expectations. A passing shortest-path unit test addresses only part of this chain.

For example, the route received → verified → resolved may be shortest and structurally valid while still being inappropriate if verification has expired. An adversarial ticket might request that the system skip an approval stage, but free-form text should not alter the permitted transition graph. The serving application must validate observations, apply policy and enforce authorization outside the planner's suggestion. Treat an algorithm's output as data that needs interpretation within a controlled workflow, rather than as an instruction that automatically grants itself permission.

## Evaluate against a meaningful baseline
A baseline is a simpler approach against which you compare a proposed system. In our example, a fixed lookup table or an existing manual procedure may already solve common cases. A planner is worthwhile only if it improves a measured outcome enough to justify its additional complexity. Define a representative set of tasks before tuning the implementation. Include ordinary cases, unusual but valid cases, missing information, disconnected graphs and attempts to request an unauthorized transition.

Evaluation needs both result quality and resource measurements. Does the returned route exist? Is its edge count minimal? Are ties handled consistently? Does the system distinguish unreachable goals from invalid input and exhausted budgets? How long does it take on the largest supported graph? A production study might also measure whether reviewed recommendations help agents complete real support work. Keep those application-level claims separate from the planner's unit-test results, and avoid inventing a percentage improvement without an actual experiment.

## Uncertainty and bounded behavior
Not every environment can be represented by a small deterministic graph. A customer can provide incomplete information, an external service can fail, and a workflow can change after a plan is computed. In such settings, the system must handle uncertainty rather than pretend every future state is known. This introduction does not implement probabilistic planning; it establishes the habit of naming the uncertainty and defining what the current implementation can and cannot guarantee.

Bounded behavior is useful even in a deterministic example. An expansion budget prevents the planner from consuming unlimited work on unexpectedly large input. Reaching that budget is not the same as proving the goal unreachable. The response should preserve the distinction so the application can retry with an authorized larger budget, ask for a narrower task or escalate to a person. Operational limits belong in the contract, not in an undocumented exception that callers mistake for a negative answer.

## When an AI component helps and when it does not
Search is appropriate when you have a meaningful state representation, legal transitions and a goal that can be checked. Rules can be preferable when the decision logic is explicit and stable. Learning can be appropriate when examples reveal useful patterns that are difficult to encode manually. Generation can be useful when the task genuinely requires creating content and the application can evaluate the result. The categories can cooperate, but none should be added merely to make an architecture sound more sophisticated.

If a task is a reliable database lookup, use a reliable lookup. If a sensitive action requires an exact policy condition, enforce that condition explicitly. If representative evaluation data is missing, describe the resulting uncertainty instead of claiming deployment readiness. AI engineering includes deciding that a model is unnecessary. This decision protects learning time, infrastructure cost and user trust while keeping attention on the problem that needs to be solved.

## What you should carry into later modules
The central habit is to connect an algorithm with its task, assumptions and evidence. You should be able to describe what the system observes, what it represents, what it proposes, who may execute the proposal and how success is measured. You should also distinguish a method's internal mathematical guarantee from a claim about a real-world outcome. A shortest path can be proven shortest under a model while remaining unsuitable in the actual environment.

Later modules introduce learned representations, neural networks, language models and tool-using agents. Those mechanisms will be more complex, but they will not remove the need for clear contracts, representative tests, controlled actions and explicit failure behavior. Return to the small graph example whenever a larger architecture becomes confusing. Ask which part is selecting a route, which part is estimating unknown information and which part has authority to change the world. Those questions provide a durable foundation for the rest of the curriculum.

## Prepare the environment
The complete example uses Python 3.12 or newer and the standard-library collections module. No additional package installation is required. Check python --version, save the code as planner.py and run python planner.py from a terminal. The course editor displays code, lets you change it and copies it to your clipboard; it does not execute Python. The expected output belongs to the unchanged reviewed example. If Python syntax is new, follow the graph and queue explanations first, then revisit the implementation after the Python foundation lesson.

We use a dictionary whose keys are nonempty string node identifiers. Each value is a list or tuple of outgoing neighbor identifiers. Every referenced neighbor must also be a dictionary key, including terminal nodes that have no outgoing edges. Start and goal must identify existing nodes. The expansion budget must be a positive integer. These input restrictions are intentionally explicit: a malformed graph should produce a validation error, not a plausible route calculated from silently ignored data.

## Understand validation and initialization
The import provides deque, a queue implementation with efficient operations at both ends. The first validation steps check that the graph is a nonempty dictionary and that its node names have the required form. The loop over adjacency lists rejects a string accidentally supplied where a neighbor list was expected. It also catches references to missing nodes before traversal starts. This up-front validation examines the whole supplied graph, even if the requested route would use only a small part of it.

The frontier queue initially contains only the start node. The parent dictionary maps the start to None, a sentinel that means the reconstruction has reached its beginning. Parent membership also serves as the discovered-node set, avoiding a separate collection with the same information. The expanded counter begins at zero. Removing a node from the queue does not necessarily expand it: if it is already the goal, the algorithm can reconstruct the route immediately. This makes a start-equals-goal request return the single start node without searching its neighbors.

## Follow traversal and reconstruction
Each loop removes the oldest queued node. If that node is the goal, the reconstruction follows parent references until reaching None, appends the visited identifiers and reverses the resulting list. Otherwise the code checks the expansion budget before inspecting outgoing neighbors. Reaching the budget raises RuntimeError so the caller can distinguish an incomplete search from a fully explored graph with no route. For every unseen neighbor, the current node becomes its parent and the neighbor is appended to the queue.

Sorting neighbors makes a choice between equally short routes reproducible. The sample graph also contains a cycle through review and verified, but discovered-node tracking prevents repeated insertion. The example returns the two-edge route received → verified → resolved. It then searches for archived, a known but disconnected node, and returns None. Finally it requests an unknown start node and catches the resulting ValueError. The program prints those three outcomes separately rather than combining them into one generic failure response.

## Expected output and debugging experiments
The unchanged program prints route: received -> verified -> resolved, missing route: None, and rejected: Unknown start or goal on three successive lines. Those statements describe this particular graph and input. To debug a different result, inspect the adjacency lists and the queue order before changing the search method. If you append neighbors to the front instead of the back, you no longer have ordinary breadth-first traversal and can lose the shortest-edge-count guarantee.

Try a graph with a self-loop and verify that it terminates. Then replace a neighbor list with a plain string; validation should reject the input before traversal. Use a tiny expansion budget on a chain with several intermediate nodes and confirm that RuntimeError is raised rather than returning None. Test start equal to goal, a terminal goal reached from another node, and a directed edge whose reverse is absent. These cases expose assumptions that a single successful demonstration would miss.

## Alternative implementations and limits
A fixed next-step table can be simpler when each state has only one approved successor. A depth-first search can find a route with different memory behavior, but does not generally guarantee the fewest edges. A weighted shortest-path algorithm is needed if transitions have meaningful nonnegative costs and the objective is total cost rather than edge count. Do not relabel this program as a cost optimizer without changing its contract and tests.

The example is small and educational. A production endpoint also needs request-size limits, typed parsing, authorization, observability and a timeout policy. The planner validates the graph structure but cannot establish that a transition is lawful or that a support problem is actually resolved. Copying the code into a service is the beginning of integration work, not evidence that those operational requirements have been met.

# industry
## A conceptual support-triage implementation
Consider a hypothetical software support team that wants consistent recommendations for handling common ticket workflows. This is an engineering case study, not a verified deployment by a named company. The team already has approved procedures, but agents sometimes miss prerequisites or send tickets down an unsuitable path. The initial proposal is a recommendation service that finds a permitted sequence of workflow stages and presents it to an agent for review. It does not automatically issue refunds, contact customers or alter accounts.

The business objective is to reduce missed procedural steps while keeping resolution quality and agent control measurable. Before implementation, collect representative workflows and identify the decisions that truly require judgment. A graph planner is useful only for the portion with explicit states and transitions. Free-form diagnosis, ambiguous policy interpretation and uncertain customer intent must remain separate problems. A system that quietly encodes all uncertainty as an edge called resolved would hide the difficult work rather than solve it.

## Represent procedures and preserve authority
Store versioned workflow definitions in a transactional database, with node identifiers, allowed transitions, applicability conditions, owners and approval records. The graph passed to the planner should reflect the workflow selected for the current product and ticket category. Request parsing validates the start state, requested goal and graph version. The planner returns a route and diagnostic metadata; an authorization layer decides which proposed steps the current agent may actually perform.

Keep tool execution outside the graph-search function. A step such as verify_account should correspond to a controlled application action with its own permission and input checks. If a proposed route contains an action requiring specialist review, the UI must show that boundary and the server must enforce it again. Never treat ticket text as an instruction to modify the approved graph. The user can describe a problem, but the workflow definition comes from trusted administration and versioned policy data.

## Serving workflow and API contracts
A small service can use FastAPI or Django, PostgreSQL for procedure versions and tickets, and the standard-library planner as a baseline. Those technology names describe a possible stack rather than dependencies required by the lesson's code. An authenticated request identifies the ticket and desired outcome. The service loads a consistent procedure version, validates the ticket's applicable scope, calculates the proposed route and returns step descriptions with the procedure version used.

Use distinct result states for invalid input, no route, exhausted budget, permission denial and successful recommendation. The client can explain each outcome without inventing success. If the procedure changes before an agent executes a recommendation, the serving path should revalidate the action against current policy. A saved plan is evidence of what was proposed at a particular time; it should not permanently authorize every step under a future policy version.

## Tests, monitoring and human review
Test graph validity and planner behavior independently from the domain policy. Unit tests cover cycles, disconnected goals, deterministic ties and resource limits. Domain tests check that workflow authors included mandatory stages and excluded prohibited transitions. Permission tests attempt to execute a valid plan through an unauthorized account. A human review exercise examines whether recommendations make sense for representative support situations, including cases with insufficient evidence.

Log procedure version, planning duration, discovered outcome class and whether a recommendation was accepted or overridden. Avoid recording raw sensitive ticket text when identifiers and structured diagnostics are enough. Review overrides with domain specialists: frequent overrides may reveal a missing state, an incorrect applicability rule or a task that should not have been represented as deterministic search. Do not equate a low override rate with good outcomes unless you have checked that agents can meaningfully question the recommendation.

## Performance, cost and rollout
For a modest graph, network and database access may dominate the cost of the search itself. Measure before introducing distributed infrastructure. Cache immutable workflow definitions by version, but continue to check current permissions and revocations at execution time. Limit graph size and request rates so a malformed or unexpectedly broad procedure cannot monopolize the service. The planner's expansion budget is one defense, not a substitute for the service's complete resource policy.

Roll out recommendations to a small authorized group, retain the existing manual workflow and compare results against the defined baseline. Track unresolved cases and procedural mistakes as well as speed. Keep a rollback path to the previous approved procedure version, and document how urgent policy changes invalidate older recommendations. The successful outcome is an auditable support process that helps people make better decisions. Using a search algorithm is simply one mechanism within that process.

Use the support example to show why an algorithmic guarantee does not automatically become a real-world guarantee. If your explanation depends on words such as intelligent or autonomous without specifying behavior, make it more concrete. You should be able to distinguish those outcomes and justify the API behavior for each one. Correct results on one happy-path example are insufficient evidence of understanding.
